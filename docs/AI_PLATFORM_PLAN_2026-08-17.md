## 0. 한 장 요약

알찬은 이미 사이드바에 **외부 학습앱 10개를 하드코딩 링크**로 달고 있다. 계정 연동 0, 보상 연동 0, 학습기록 0.
"플랫폼화"란 이 링크 목록을 **규약(AAP)** 으로 승격시켜, 알찬이 *계정·화폐·보상·학습기록의 코어*가 되고
학습앱들은 각자 호스팅을 유지한 채 꽂히는 구조로 바꾸는 일이다.

### 교차검증이 뒤집은 것 (초안 v0 → 최종)
| # | 초안 v0 의 판단 | 검수 후 결론 |
|---|---|---|
| 1 | 데이터는 당연히 서울 리전에 있다 | ❌ **DB 가 미국(nam5)에 있다.** 아동 데이터 국외이전 + 비용 1.5배 + 태평양 왕복 (§2.2) |
| 2 | 읽기 절감이 전국 개방의 **전제조건** | ❌ 아니다. 진짜 전제조건은 **테넌트 격리**. 비용은 게이트가 아니라 기울기다 |
| 3 | 수익화는 "나중에" | ❌ **학급 수 임계**로 정의해야 한다(약 44학급). 그리고 **선행조건이 기술이 아니라 겸직 허가**다 (§6.3) |
| 4 | 개학(2주 뒤)에 1차 투입 | ❌ 개방은 **내년 3월**. 2학기는 본인 학급에서 규약을 검증하는 기간 |
| 5 | 보상 API 는 클라가 `amount` 를 보내고 서버가 캡으로 막는다 | ❌ **캡이 방어가 아니라 가격표가 된다.** 서버가 성취별로 금액을 확정해야 한다 (§2.4 C1) |
| 6 | SSO 토큰은 재생돼도 피해가 없어 nonce 불필요 | ❌ 탈취자가 **피해자의 일일 캡을 태워버린다** (§2.4 C5) |

**가장 중요한 세 문장**
1. **불변식 "다른 학급 데이터를 읽을 수 없다"는 오늘 이미 깨져 있다.** `jobs`·`storeItems`·`commonTasks`·`goals` 등 7개 컬렉션의 읽기 규칙이 `if isSignedIn()` 뿐이다. 2026-07-19 하드닝이 **쓰기만 잠그고 읽기는 "클라가 classCode 로 쿼리하니까"로 두었다** — 클라이언트 쿼리는 보안 통제가 아니다. **고치는 데는 각 1줄, 반나절이다.**
2. **DB 가 미국(nam5)에 있다.** 아동 데이터 국외이전 + 비용 1.5배 + 함수(서울)↔DB(미국) 태평양 왕복. 서울 이전 하나가 셋을 동시에 푼다.
3. **진짜 병목은 읽기 비용이 아니라 주급 스케줄러다.** `users` 를 두 번 전량 스캔하고 학급을 순차 처리하는데 타임아웃은 540초 고정 — **약 190~630학급에서 붕괴**한다(2계열 독립 추정). 이 함수는 주급 지급이고, 저장소엔 이미 `reverseLastWeeklySalary`(과거 중복지급 사고의 흔적)가 있다.

### 그래서 지금(개학 전)은 무엇을 하는가
개방을 미룬다고 지금 할 일이 없는 게 아니다. **개방과 무관하게 내 학급에 바로 이득이고 되돌리기 쉬운 것**부터 한다.

| 지금 할 것 | 얻는 것 | 크기 |
|---|---|---|
| **읽기 유출 7건 봉인** | 오늘 열려 있는 크로스테넌트 읽기를 닫는다 | **각 1줄** |
| **전역 설정 쓰기 좁히기**(`Settings`·`classCodes`·`laws`) | 승인 교사가 전국 설정을 만지는 것을 막는다 | 작음 |
| **주급 스케줄러 중복 스캔 제거 + 시간 예산 가드** | 부분 지급 사고를 막는다 | 작음 |
| `classes/{classId}` 정본 | 스케줄러 전량 스캔 제거 · 수익화 뼈대 · 온보딩 그릇 | 중간 |
| 앱 레지스트리 + 사이드바 데이터화 | 새 학습앱 추가가 **코드 배포 → 문서 수정** | 작음(정정) |

전부 P0(§10)이고, **하나도 되돌리기 어려운 변경이 아니다.**
정리하자면 — **규약은 지금 만들고, 문은 3월에 연다.**

### 2.1 Tier-0 결정론 검사 — 메인 직접 실측

#### CRITICAL-1. `isAdmin()` 이 학급 스코프가 아니다 ★개방의 절대 차단기
`firestore.rules:24` 의 `isAdmin()` 은 "승인된 관리자인가"만 본다. **classCode 대조가 없다.**
학급 스코프 버전(`isClassAdmin(classCode)` :65, `isClassAdminOfUser(userId)` :78)이 따로 있는데, 쓰이는 비율이 낮다.

| 함수 | 학급 스코프 | 사용 횟수 |
|---|---|---:|
| `isAdmin()` | ❌ | **112** |
| `isAdminFast()` | ❌ | **69** |
| `isClassAdmin(...)` | ✅ | 45 |
| `isClassAdminOfUser(...)` | ✅ | 14 |

**비스코프 181 vs 스코프 59.** 성격별 분포: read 65 · delete 39 · update 17 · create 14 · write 7 · 헬퍼 내부 37.

→ 전국 개방 = **승인된 아무 교사나 전국 아무 학급의 완전한 관리자**가 된다.
→ 지금 문제가 없는 이유는 교사가 5명이고 전원 신뢰 관계이기 때문이다. 개방이 그 전제를 없앤다.
→ 이건 새 발견이 아니다. 프로젝트 기록에 **"P1 isAdmin 학급스코프 — 미착수"** 로 이미 있던 부채다.
   **부채가 아니라 개방의 차단기로 재분류해야 한다.**

#### CRITICAL-2. 전역 열람 규칙 22곳
`allow read: if isSignedIn();` 단독이 **22곳**. 확인한 예: `goals`(:900) · `marketListings`(:1468) ·
`marketOffers`(:1481) · `nationalTax`(:1402).
→ 개방 즉시 전국 학생이 서로의 학급 데이터를 읽는다. 2학급에서는 증상이 없다.

> **내 1차 판단의 오류를 정정한다.** 처음엔 "classCode 문자열이 없는 top-level 블록 20/61" 을 전부 구멍으로 봤다.
> 실제로 열어보니 `marketListings`·`marketOffers`·`nationalTax` 는 `create/update/delete: if false`(CF 전용)로,
> `goals` 는 `isAdmin()` 으로 이미 하드닝돼 있었다. **쓰기는 잘 막혀 있다. 문제는 읽기와 isAdmin 스코프다.**

#### CRITICAL-3. 스케줄러가 학급 수에 비례해 터진다
`functions/scheduler-http.js:2064`
```js
async function getAllActiveClassCodes() {
  const snap = await db.collection("users").where("isAdmin","==",false).get();  // 필터가 isAdmin 뿐
  ...
}
```
**학급 코드 목록을 얻으려고 전국 학생 전원을 읽는다.** 호출부 5곳(:1067, :2125, :2187, :2499, :2818).
주석은 "settings/classCodes 에 의존하지 않으므로 신규 학급도 자동 포함" 이라고 적혀 있다 —
2학급에서는 옳은 설계이고 1,000학급에서는 재앙이다.

| 위치 | 함수 | 빈도 | 위험 |
|---|---|---|---|
| `:2065` | `getAllActiveClassCodes()` | **스케줄러 실행마다** | 25,000명 기준 1회 25,000읽기 → 시간별 실행 시 **하루 60만 읽기**(학생 활동과 무관한 순수 오버헤드) |
| `:2199` | `payWeeklySalariesLogic()` | 주 1회 | 단일 실행에서 전원 처리 → **함수 타임아웃·메모리 한계** |

같은 안티패턴이 `SuperAdminDashboard.js:194` 에도 있다(학급·학생 집계를 전체 users 스캔으로) — **3곳째다.**

> 타학급 액터 `farStu`(classCode C2)가 **10회** 쓰인다(`:68` 정의, `:185/:277/:287/:292` 등).
> 내 grep 이 "다른 학급/crossClass" 같은 키워드를 찾느라 **액터명을 못 잡았다.**
> 남는 문제는 "교차학급 케이스가 없다"가 아니라 **대상 컬렉션이 5개뿐**이라는 커버리지다.
> 그리고 §2.4 에서 드러나듯 **실제로 새는 컬렉션들은 그 5개에 들어 있지 않다.**

또한 이 스위트는 **CI 에 물려 있지 않다**(로컬 Firebase 로그인 필요 → CI 제외).
반면 `deploy.yml` 은 rules 를 **자동 배포**한다 — 검증 없이 배포되는 구조다 (codex A13).

#### HIGH-5. 동의서와 실제 수집 항목이 어긋난다
`ConsentForm.js` 는 수집 항목을 **닉네임·학급코드**로 명시하는데,
`StudentManager.js` 에는 경로가 둘 있다 — `:242` 일괄 생성은 `name: id`(최소화, `:793` "이름을 수집하지 않아 안전"),
그러나 `:195/:669/:1103` 개별 추가·수정에는 **"학생 이름" 입력 필드가 실재**한다.
→ 교사가 실명을 넣으면 처리방침에 없는 항목을 수집하게 된다. 개방 전 반드시 닫아야 한다.

#### MEDIUM-6. 읽기 절감 목표(1,775→300)는 근거가 약하다 — v0 의 오류
- 이미 3단계 절감을 마쳤고 `docs/PERF_REVIEW_2026-08-12.md` §5 "손댈 게 없던 것(재조사 금지)" 목록이 길다
- 남은 B1~B11 은 대부분 **세션당 한 자릿수** 절감
- 페이지 이동 1회 ≈ **36읽기가 구조적 바닥**이고 그중 89%는 낭비가 아니라는 기록이 있다
→ 5.9배 절감은 미세최적화로 불가능하다. 아키텍처 변경(학급 단위 스냅샷 등)이 필요하다.
→ **그리고 애초에 이건 개방의 전제조건이 아니다** — §6 비용 곡선 참조.

#### 검산 — v0 비용표는 대체로 맞았다
서울 Firestore 읽기 단가 **$0.38/100만**(Cloud Billing Catalog API 실측)을 확인했다.
흔히 인용되는 $0.06/10만은 US 멀티리전 값이라 6배 이상 비싸게 잡히는 함정이 있다.
다만 v0 는 읽기만 계산했다 → 쓰기·함수호출·에그레스를 포함하고 무료한도를 차감해 §6에서 다시 계산했다.

### 2.2 ★가장 큰 발견 — Firestore 가 **미국(nam5)** 에 있다

Gemini 가 "Firebase 기본 설정 사용 시 아동 데이터 국외이전 위반"을 지적했다.
Cloud Functions 가 서울 리전이라 **오탐이라 판단하고 넘어갈 뻔했다.** 확인해 보니 아니었다.

```
$ firebase firestore:databases:get "(default)"
  Location  nam5            ← 미국 멀티리전 (Iowa·South Carolina)
```
`firebase.json:163` 에도 `"location": "nam5"` 로 박혀 있다.

**한국 초등학생의 학급 데이터 전체가 미국에 저장되고 있다.** 파급이 셋이다.

**(1) 법** — 처리방침에 국외이전 조항은 **있다**(`PrivacyPolicy.js:232`). 그런데 문구가
"…**일부 기술적 처리(보안 모니터링 등)** 가 국외에서 이루어질 수 있습니다"다. 실제는 **DB 전체**다.
법정대리인 동의서(`ConsentForm.js`)에는 국외이전 언급이 **0건**이다.

**(2) 비용** — 비용표를 서울 단가로 계산했는데 nam5 는 US 멀티리전 단가다. **약 1.5배**(§6).

**(3) 속도** — Functions 는 서울, DB 는 미국. **함수 호출마다 태평양 왕복**이 일어난다.
성능 리뷰는 전송 바이트를 봤지만 **리전 지연은 아무도 안 봤다**.

→ **서울 이전이 단일 항목으로 가장 값어치가 크다** — 비용 1.5배 여유 + 법적 쟁점 소멸 + 지연 제거.
⚠️ Firestore 위치는 **변경 불가**다. 새 DB 생성 + export/import + 코드의 DB 참조 전량 교체 →
**겨울방학이 유일한 창**이다.

### 2.4 테넌트 격리 — 불변식 #1 은 **오늘 이미 깨져 있다**

내 초기 조사는 `allow read: if isSignedIn();` 이 22곳이라는 **집계**까지였다.
claude-feas 와 codex 가 **어느 컬렉션이 실제로 새는지**를 특정했고, 메인이 코드로 확인했다.

#### (1) 읽기 유출 — 쓰기는 잠갔는데 읽기를 안 잠갔다
```
firestore.rules:812   match /jobs/{jobId}
                        // 읽기: 로그인한 사용자, classCode 쿼리 허용   ← 이 주석이 함정이다
                        allow read: if isSignedIn();
                        // 🏫 Phase1(2026-07-19): jobs는 classCode 필드 보유 → 자기 학급 직업만 관리
```
2026-07-19 하드닝이 **쓰기만** 학급 스코프로 잠그고, 읽기는 *"클라이언트가 classCode 로 쿼리하니까 괜찮다"* 로 두었다.
**Firestore 규칙은 문서 단위로 평가된다.** 필터 없는 `getDocs(collection(db,'jobs'))` 는 규칙이 허용하는 **전부**를 반환한다.
클라이언트의 쿼리는 보안 통제가 아니다.

| 컬렉션 | 줄 | 새는 것 |
|---|---|---|
| `jobs` | 812 | 전국 직업·급여 카탈로그 |
| `storeItems` | 529 | 전국 상점 카탈로그 |
| `commonTasks` | 827 | 전국 공통과제 |
| `taxSettings` | 890 | 전국 세율 |
| `goals` | 901 | 전국 쿠폰목표 |
| `marketListings` / `marketOffers` | 1468 / 1483 | 전국 거래·오퍼 활동 |
| `realEstate` | 667 | (문서 0건이라 실피해 없음, 구조는 열림) |

2학급에서는 "옆반 카탈로그가 보인다" 수준이라 무해했다. **전국 개방에서는 불변식 #1 의 정면 위반**이다.
과거 rules 감사 3회가 이걸 놓친 이유도 밝혀졌다 — 감사가 `isSameClassFast` **호출 횟수**를 셌는데,
**헬퍼를 아예 부르지 않은 컬렉션은 애초에 세어지지 않는다.**

#### (2) 전역 설정 쓰기 — 승인 교사면 플랫폼을 만진다
| 위치 | 규칙 | 결과 |
|---|---|---|
| `Settings/{documentId}` :859 | `write: isAdmin() \|\| (isSignedIn() && documentId=='activeStatus')` | 승인 교사 누구나 **`scheduler.vacationMode` 등 플랫폼 전역 설정** 조작 |
| `settings/{documentId}` :872~876 | salarySettings_ 패턴이 아니면 `isAdmin()` 통과 | 승인 교사 누구나 **`settings/classCodes`(전역 유효 학급코드)·`mainSettings`(화폐단위)** 덮어쓰기 |
| `laws` update/delete :1460 | `isAdmin()` — classCode 검사 없음 | **LIVE** (`OrganizationChart.js:295,330` 클라 직접 호출) — 타 학급 법안 편집·삭제 |
| `learningMaterials` :712 · `musicRooms` :1278 | `isAdmin()` | 타 학급 자료·음악방 조작 |

rules 주석(:62)이 *"전역 공용 컬렉션은 학급 스코프가 무의미하므로 `isAdmin()` 유지"* 라고 **설계 전제를 명시**한다.
그 전제는 **"isAdmin = 내가 수동 승인한 신뢰 교사 5명"** 일 때만 성립한다.
**교사 온보딩 자동화(P2-5)가 이 전제를 정면으로 깬다.** 순서를 지키지 않으면 자동화 배포 즉시 구멍이 열린다.

#### (3) 학급 이동 직후 두 학급이 동시에 열린다
`isSameClassFast` 는 "토큰 클레임 일치 **OR** users 문서 일치"의 OR 조건이다.
학생이 C1→C2 로 옮기면 **토큰 갱신 전까지 C1(클레임)·C2(문서)가 둘 다 통과**한다. (codex)

#### (4) 죽은 컬렉션 하드닝이 2개 빠졌다
`/realEstate`(667)·`/trials`(677)는 클라 참조 0건인데 `auctions`·`treasury`·`nationalTax` 와 달리 `if false` 처리가 안 됐다.
**4개 중 2개를 놓쳤다는 사실 자체가** "1,550줄이니 전수 봤다"는 자신감에 대한 반증이다 — 전수조사는 항상 몇 개를 놓친다.

| **A11** | `tenants = 학급` 모델은 **한 교사·학교의 여러 학급 공통 플랜을 표현 못 한다** | `tenantId` 와 `classId` 분리 |

| **A13** | rules 테스트가 **CI 에 물려 있지 않다**(로컬 Firebase 로그인 요구로 CI 제외). deploy 는 rules 를 자동 배포한다 | Emulator + `@firebase/rules-unit-testing` 로 전환해 **배포 게이트로** |

| **A15** | 학교 이메일 인증은 **교사 자격 증명이 아니다** | 이메일 확인 계정은 제한된 trial, 자격 확인은 별도 단계 |

그 밖에 채택: 앱 긴급 철회 절차 · 보상 append-only ledger + 대사 · 학습이벤트의 uid/classCode/ts 를
**요청값이 아니라 서버 세션에서 결정** · CORS/redirect allowlist · rate limit·hard quota · 스케줄러 DLQ.

## 3. 목표 아키텍처 — 알찬은 코어, 앱은 위성

위성앱을 알찬 번들로 **흡수하지 않는다.** 2026-08-03에 게임 7,007 LOC + three.js 875KB + 에셋 12.4MB를 들어내고, 이어서 아바타 WebP 전환·base PNG
최적화까지 한 결과 build 는 99MB → **현재 5.6MB**(JS 청크 2.2MB)다. 이 성과를 되돌리지 않기 위함이다. 앱은 각자 호스팅에 남고, **규약으로만** 붙는다.

### 3.0 규약이 실제로 사주는 것 (현재 위성앱의 실상)
추상적인 "플랫폼화"가 아니라 지금 무엇이 안 되는지부터 본다. 위성앱들의 현재 신원 관리를 확인했다:
- **타이핑버스** — `localStorage` + 학생이 직접 입력한 닉네임. 계정 없음 (`iwtaping/src/app/ranking/page.tsx:35`)
- 대부분의 앱이 같은 방식이고, `iwart` 만 자체 Firebase 를 따로 쓴다

그래서 지금 이런 일이 벌어진다:
| 증상 | 원인 |
|---|---|
| 학생이 기기(교실 PC ↔ 태블릿)를 바꾸면 **기록이 사라진다** | 기기 로컬 저장 |
| 교사가 **누가 얼마나 했는지 모른다** | 학습기록이 알찬에 없다 |
| "랭킹"이 학급 랭킹이 아니라 **그 기기의 랭킹**이다 | 서버 신원 없음 |
| 학습 성과가 **학급경제와 무관**하다 | 보상 연동 없음 |
| 앱이 늘수록 학생이 외울 것이 는다 | 앱마다 따로 놂 |

**AAP 가 사주는 것은 정확히 이 다섯 줄이다.** SSO 그 자체가 목적이 아니다.

### 3.1 설계 원칙 (codex 교차검증 후 개정)

**원칙 1. 지급 경계와 진위 경계는 다른 곳에 있다.**
- **지급 경계 = 알찬 서버.** 보상은 알찬 서버가 토큰을 검증한 뒤에만 나간다. 위성앱의 토큰 검증은 로컬 판단일 뿐이다
- **진위 경계 = 위성앱.** "이 학생이 정말 100점을 받았는가"는 **알찬이 독립적으로 검증할 수 없다**
- 이 둘을 혼동하면 안 된다. 서버가 있다고 진위가 보장되지 않는다 —
  **앱 서버가 클라이언트의 "완료" 주장을 그대로 서명하면 신뢰등급만 올라간 세탁기가 된다**(codex C3)
- → 그래서 L2 의 정의는 "자체 서버 보유"가 아니라 **"서버가 성취를 독립 검증"** 이다

**원칙 2. AAP 는 보안 설계가 아니라 _부정 지급 손실 제한_ 설계다.**
캡은 위조를 막지 않는다. **캡만 있으면 공격자는 매일 확정적으로 최대치를 가져간다 — 캡이 방어가 아니라 가격표가 된다.**
따라서 손실 제한은 캡 하나가 아니라 다음의 조합이어야 한다:
1. **서버가 금액을 정한다** — 클라는 "무엇을 달성했는지"만 보내고, 금액·타입은 서버 카탈로그가 확정 (C1)
2. **성취마다 허용 횟수·선행조건·쿨다운** — 가장 비싼 성취의 무한 반복을 막는다 (C2)
3. **레이트리밋 + 차단기** — 캡만으로는 함수 호출·트랜잭션 재시도 비용 공격을 못 막는다 (C11)
4. **앱별 kill switch** — 문제가 보이면 즉시 끈다. **이 스위치는 절대 캐시하지 않는다** (C13/C22)
5. **감사 + 환수** — 사후에 되돌릴 수 있어야 한다 (C17/C22)
6. **교사 가시성** — 이상치를 교사에게 보여준다. 이 앱에는 법원·경찰서가 있고 학급 내 사회적 제재가 실제로 작동한다

### 3.2 AAP 토큰
- **RS256 고정**(`alg` 를 검증에서 고정 — `none`/HS 다운그레이드 차단), `kid` 로 키 식별, **키 회전**(중복기간 운영)
- `iss`(알찬) · `aud`(대상 appId) · `jti` · `iat`(최대 허용 나이) · `exp`(5분) 전부 검증한다 (C7)
- **`sub` 는 앱별 pairwise 식별자**로 만든다 — 같은 uid 를 10개 앱에 그대로 주면
  **외부 운영자들 사이에서 학생을 연결하는 추적 식별자**가 된다 (C21)
- **`nick`·`cls`·`role` 은 기본 미포함.** 앱이 정말 필요하다고 심사에서 인정된 경우에만 선택적으로 (C21)
- **실행 URL 은 서버가 정한다** — 요청자가 지정하면 fragment 토큰을 공격자 사이트로 보낼 수 있다.
  서버는 **레지스트리에 등록된 정확한 origin/path 로만** 리다이렉트한다 (C6)
- 전달은 URL fragment(`#t=`). 쿼리스트링 금지

> **재생 방어 — 처음엔 nonce 를 뺐다가 되돌렸다.**
> 초안의 논리는 "SSO 토큰을 재생해도 같은 학생이 앱을 다시 열 뿐이라 피해가 없다"였다. **틀렸다.**
> fragment 토큰은 같은 origin 의 JS·분석 SDK·XSS·브라우저 기록에서 읽힌다. 탈취자는 멱등키를 바꿔가며
> **피해자의 일일 캡을 먼저 소진**시킬 수 있다 — 보상 탈취 + 정상 지급 거부 + 학습통계 오염이 동시에 일어난다 (C5).
> 다만 전면 nonce(앱 실행마다 서버 쓰기 1건 = 하루 12.5만 쓰기)가 답은 아니다. **계층화한다**:
> `jti` 로깅 + 짧은 TTL + **보상을 동반하는 실행만 1회용 세션** + 재생 탐지.

### 3.3 보상 API — `grantAppReward`

**핵심 변경: 클라이언트는 금액을 보내지 않는다.**
```
요청  { token, achievementId, clientRunId }      ← amount·rewardType 없음
서버  achievements/{appId}/{achievementId} 에서 금액·타입·횟수·쿨다운을 확정
```

**서버 소유 achievement 카탈로그** (신설 — 초안에 아예 없던 것)
```
achievements/{appId}/items/{achievementId} = {
  label, rewardType: "cash"|"coupon", amount,      // 서버만 안다
  maxPerDay, maxLifetime, cooldownSec, prerequisites[],
  policyVersion, revocable: true
}
```

**검증 순서** (④↔⑤ 교체 — codex C9)
1. 토큰 검증 — 서명·`alg` 고정·`iss`/`aud`/`exp`/`iat`/`kid`. **`appId` 는 입력값이 아니라 검증된 `app` 클레임에서** (C7)
2. **현재 membership 재확인** — 토큰의 `cls`/`role` 만 믿으면 전학·퇴출 후에도 유효하다 (C8)
3. 앱 상태 조회 — **kill switch 는 캐시하지 않고 직접 읽는다** (C13)
4. **멱등 조회 먼저** — 트랜잭션 안에서 `(uid, appId, key)` + **요청 해시**로 기존 결과를 찾는다.
   캡 검사를 먼저 하면 **정상 재시도가 캡 때문에 실패**한다. 같은 키에 다른 payload 면 성공 반환이 아니라 **충돌** (C9/C10)
5. 카탈로그에서 금액 확정 → 횟수·쿨다운·선행조건 검사
6. 레이트리밋·차단기 (C11)
7. **한 트랜잭션**에 지급 + 멱등 레코드 + 지급로그 + 통계. 경합 시 `ABORTED` 를 정상 경로로 처리 (C-트랜잭션)

**신뢰등급 재정의** (C3)
| 등급 | **의미** | 허용 보상 |
|---|---|---|
| **L0** | 검증 불가 — 정적 클라이언트가 주장하는 성취 | 명목상 소액만. **경제적·학업적 가치가 큰 보상 금지** |
| **L2** | **앱 서버가 성취를 독립 검증** (클라 주장을 그대로 서명하는 것은 L2 가 아니다) | 정상 캡 |
> 초안의 "L1 = 서버 없음 / L2 = 서버 있음"은 **서버의 존재와 검증을 혼동**한 것이라 폐기했다.

### 3.4 학습기록
초안의 키 `learningStats/{classCode}_{uid}_{yyyymmdd}` 는 **두 가지가 틀렸다**:
- **키 충돌** — `classCode="a_b", uid="c"` 와 `classCode="a", uid="b_c"` 가 같은 ID 가 된다 (C14)
- **ID 안의 값은 필드가 아니라 쿼리할 수 없다** — 교사 대시보드의 학급×기간 조회가 불가능하다 (C15)

**개정**
```
classes/{classId}/learningStats/{uid}/days/{yyyymmdd}/apps/{appId}
  = { classId, uid, date, appId, sessions, sec, best, updatedAt }   // 전부 명시 필드
```
- 계층 경로 → 충돌 없음, 학급 범위 쿼리 가능
- **앱별로 분리** → 학생이 여러 앱을 병렬 실행해도 문서 경합이 없다 (C16)
- **원시 audit 이벤트를 보존한다**(보존기간 제한). 집계만 남기면 **부정 지급 조사·정책 변경 후 재계산·통계 복구가 불가능**하다 (C17)

### 3.5 앱 레지스트리 — 카탈로그와 정책을 **분리**한다
초안은 "단일 문서 vs 앱별 문서"의 양자택일로 봤는데 **거짓 이분법이었다**(C12). 축이 둘이다:

| | 무엇 | 어디 | 캐시 |
|---|---|---|---|
| **공개 카탈로그** | 사이드바 표시용(이름·아이콘·URL·과목) | 단일 문서 1개 | ✅ 버전 문서로 무효화 |
| **집행 정책** | 캡·kill switch·trustLevel·허용 origin | 앱별 문서 | ❌ **캐시 금지** — 실행/지급 시 직접 조회 |

- 표시는 1읽기, 정책은 **실제로 쓰는 앱 1개만** 읽는다 → 초안이 걱정한 "매 세션 10읽기"가 애초에 발생하지 않는다
- **차단 스위치가 stale 캐시에 묻히는 사고**를 구조적으로 막는다 (C13)
- 단일 문서의 1MiB 한계·장애 반경 문제도 정책이 빠지면서 완화된다

### 3.6 `classes` — 학급의 정본
현재 `classes/{classCode}` 는 서브컬렉션의 부모 경로일 뿐 메타 문서가 없다.
학급 목록은 **클라이언트(`SuperAdminDashboard.js:693`)가 관리하는** `settings/classCodes` 의 배열 2개뿐이고,
스케줄러는 그걸 믿지 못해 **전국 users 를 전량 스캔**한다. 고칠 것은 스캔이 아니라 **정본의 부재**다.

**개정 설계** (codex C18/C19/C20 반영)
```
classes/{classId}                     // ★ 불변 랜덤 ID — 사람에게 보이는 코드가 아니다
  { classId, teacherUid, schoolName?, grade?, createdAt, status,
    joinCode,                          // ★ 회전 가능. 노출·재사용돼도 통계가 섞이지 않는다
    plan: "free"|"school"|"pro" }      // 설정만
classes/{classId}/counters/usage       // ★ 사용량은 별도 문서 — 학급 전원이 설정 문서에 경합하지 않는다
classes/{classId}/apps/{appId}         // 학급별 앱 on/off
```
- **`classCode` 를 영구 PK 로 쓰지 않는다.** 코드를 재사용·변경하면 과거 통계와 새 학급이 합쳐진다 (C18)
- **마이그레이션은 재검증부터** — 클라이언트가 관리하던 목록은 신뢰 원본이 아니다.
  교사 소유권·실제 membership 으로 대조해 승격한다. 안 그러면 **가짜 학급이 정본이 된다** (C4)
- **신규 경로 rules 는 default-deny** 로 시작하고 교사·학생·관리자·타 학급 **접근 매트릭스 테스트**를 붙인다 (C20)
- 이행은 backfill → 대조 → 점진 cutover → fallback 제거 순서. 이중 경로 기간의 **split-brain** 을 감시한다

이 정본 하나가 동시에 해결하는 것: 스케줄러 전역 스캔(§2.1 CRITICAL-3) · SuperAdminDashboard 전역 집계 ·
`settings/classCodes` 배열 병목 · 수익화 플랜의 저장 위치 · 교사 온보딩의 산출물.

### 3.7 규약 버전·운영 (초안에 없던 것 — codex C22/C23)
- **AAP 버전**(v1) 과 폐기 일정, 앱 인증키 회전, **장애 시 fail-closed**(의심스러우면 지급하지 않는다)
- 앱별 kill switch · 지급량/호출량 경보 · 예산 상한 · 감사로그 · **환수(revoke)** 절차 · 개방 전 부하 테스트

### P4(C) — 알찬 내장 AI
플랫폼(A)이 서면 **AI 가 쓸 데이터가 처음으로 생긴다.** 지금 알찬에는 AI 를 붙일 만한 통합 데이터가 없다 —
학습기록이 없고(위성앱은 localStorage), 학급 상태는 60여 개 컬렉션에 흩어져 있다.
`learningStats`(§3.4)와 `classes`(§3.6)가 생긴 뒤라야 C 가 의미를 갖는다. **이게 A→C 순서의 진짜 이유다.**

**교사용 (가치가 가장 크다 — 교사의 시간을 직접 돌려준다)**
| 기능 | 입력 데이터 | 왜 지금은 못 하나 |
|---|---|---|
| 주간 학급 리포트 자동 생성 | `learningStats` + 거래·활동 로그 | 학습기록이 없다 |
| 이번 주 할일/퀘스트 제안 | 학급의 직업·할일 이력 + 학습 취약점 | 취약점 데이터가 없다 |
| 경제 이벤트 시나리오 생성 | 학급 물가·자산 분포 | 가능하지만 지금은 수작업 |
| 학생별 코멘트 초안 | 학습·경제 활동 요약 | 통합 뷰가 없다 |

**학생용 (안전 요구가 질적으로 다르다)**
초등학생 대상이라 **안전 필터는 타협 대상이 아니다.** 자유 대화형은 마지막에 두고,
**구조화된 형태**(오답 힌트, 학습 도우미, 정해진 주제)부터 연다.

**비용 통제 — 기능보다 먼저 넣는다**
- 무료 개방 + LLM 종량과금 = **즉시 적자**다. §6.1 의 인프라 비용과 자릿수가 다르다
- `classes.plan` 에 **월 토큰 쿼터**를 걸고, 초과 시 기능이 꺼지는 게 아니라 **정상 degrade**(캐시된 리포트 유지 등)
- 교사용부터 여는 이유: 호출 빈도가 학생용보다 2~3자릿수 낮다(학급당 주 1회 vs 학생당 수시)

### P5(B) — 생성형 단계 (범위 축소)
교차검증에서 **자연어 미니앱 빌드는 교사 수요가 낮고 편향·저작권·오개념 민원 리스크가 크다**는 지적이 나왔고,
codex 는 **미검증 보상 경계를 증폭시킨다**고 봤다. 그래서 범위를 줄인다.

- ❌ 교사가 자연어로 **임의 코드 앱**을 만드는 것 → 보류
- ✅ **교육과정 기반 활동/퀴즈 템플릿 생성기** — 교사가 원하는 건 "진도 맞춤 퀴즈 원클릭"이지 앱 코딩이 아니다
- 생성물의 보상은 **L1 = 경제 보상 0**(§2.6 A2) 고정. 실행은 샌드박스 iframe + CSP
- 진입 조건: L1 보상 0 · capability model · kill switch · 규약 적합성 테스트 통과

→ P1~P3 의 규약이 실전 검증된 뒤에만 의미가 있다. **순서를 당기지 않는다.**

→ P0-5. 실명 입력 경로를 막는 쪽을 권장한다(동의 관리 부담이 없어진다).

### 5.2b 국외이전 — 고지가 실제보다 축소돼 있다 ★
처리방침에 국외이전 조항이 **있다**(`PrivacyPolicy.js:232`). 문구는 이렇다:
> "Google LLC 본사는 미국에 있으며 … **일부 기술적 처리(보안 모니터링 등)** 가 국외에서 이루어질 수 있습니다"

실제는 "일부 기술적 처리"가 아니라 **데이터베이스 전체가 미국(nam5)** 이다(§2.2 실측).
그리고 법정대리인 **동의서(`ConsentForm.js`)에는 국외이전 언급이 0건**이다.
개인정보보호법 제28조의8 은 이전받는 자·항목·국가·목적·보유기간을 알리고 **별도 동의**를 받도록 한다.
→ 두 갈래 중 하나를 골라야 한다: **(A) 서울로 이전해 쟁점을 없앤다**(권장·§4 P2-0) / (B) nam5 유지 + 고지·동의 정비.

### 5.3 개인정보 최소화를 AAP 에도 관철한다
AAP 토큰 클레임에 **실명·학번을 넣지 않는다**(§3.2). 더 나아가 교차검증 지적을 받아 **앱별 pairwise `sub`** 를 쓴다 —
같은 uid 를 10개 앱에 그대로 주면 **외부 운영자들 사이에서 학생을 연결하는 추적 식별자**가 되기 때문이다(§2.4 C21).
`nick`·`cls`·`role` 도 기본 미포함이고, 앱이 필요를 입증한 경우에만 선택적으로 준다.
→ 학습앱이 늘어나도 개인정보가 퍼지지 않는다. **이건 규약 설계 단계에서만 공짜로 얻을 수 있는 성질**이다.
   나중에 되돌리려면 앱 10개를 전부 고쳐야 한다.

### 5.4 개방 시 새로 생기는 법적 지위 (P2-7)
무료라도 전국 학생 데이터를 다루면 **개인정보처리자**의 의무가 발생한다.
개인이 운영자가 되는 것의 책임 범위, 학교 밖 서비스에 대한 학교·교육청의 승인 절차,
만 14세 미만 동의의 실무적 수집·보관 방법 — 이 셋은 **기술 문제가 아니라 절차 문제**이고,
개방 일정을 실제로 좌우할 수 있다. 3월 개방을 목표로 한다면 **겨울방학 전에 조사를 시작**해야 한다.

### 6.2 사비 한계선 — 이 표가 수익화 시점을 정한다
| 월 예산 | 초안(서울 가정) | **nam5 실제** | nam5 + 읽기 절반 | **서울 이전 시** |
|---|---:|---:|---:|---:|
| ₩30,000 | 42학급 | **28학급** | 50학급 | 42학급 |
| **₩50,000** | 67학급 | **44학급** | 78학급 | **67학급** |
| ₩100,000 | 127학급 | **84학급** | 147학급 | 127학급 |

**결론 세 가지**
1. **무료 개방의 자연 상한은 약 44학급**이다(월 ₩5만 기준). 초안이 말한 67학급이 아니다
2. **서울 리전 이전이 읽기 절감과 맞먹는 지렛대다** — 이전만으로 44 → 67학급(1.5배).
   읽기를 절반으로 줄이는 것(44 → 78학급, 1.8배)과 같은 급인데, **법적 리스크와 지연시간까지 함께 해결한다**(§2.2)
3. **수익화는 시간이 아니라 학급 수로 정의한다.** 44학급(또는 이전 후 67학급)에 도달하기 *전에* 과금 스위치가 준비돼 있어야 한다

### 6.3 ⚠️ 수익화의 선행조건은 기술이 아니다 — 겸직 허가
Gemini 가 짚은 것 중 내가 완전히 놓쳤던 축이다(§2.3 G6).
**현직 교원은 국가공무원법 제64조에 따라 영리업무가 금지되고, 겸직은 사전 허가 대상이다.**
- 무료 운영과 **수익 발생**은 법적 지위가 다르다
- 유료화·플랫폼 소유권 행사 이전에 **소속 학교·교육청의 겸직 허가**가 선행되어야 한다
- 이건 코드로 해결할 수 없고, **절차 소요 시간이 길 수 있다** → 임계(44학급)에 닿기 훨씬 전에 알아봐야 한다

### 6.4 결제 경로 — 학교 공금은 원천 불가다 (G7)
| 경로 | 가능한가 | 조건 |
|---|---|---|
| 학교 예산(K-에듀파인) | ❌ 현재 불가 | **사업자등록·전자세금계산서·통장사본**이 필요. 개인 상태로는 학교 공금 결제 자체가 안 된다 |
| 교사 개인 카드 | ⚠️ 가능하나 저항 큼 | 수업용 사비 지출 저항이 크다. 무료로 쓰던 사용자의 이탈을 각오해야 한다 |
| 학교·교육청 사업 | ⚠️ | 별도 조달 절차 |
→ **무료로 시작해 나중에 과금**하는 계획은 이 표를 먼저 풀어야 성립한다.

### 6.5 그래서 지금 심어야 할 것 (과금은 나중에 켜더라도)
`classes/{classId}` 계열에 처음부터 넣는다 — 나중에 넣으면 전 학급 마이그레이션이 된다.
- `plan: free|school|pro` (설정 문서)
- `counters/usage` **별도 문서** — 학급 전원이 설정 문서에 경합하지 않게 (§3.6)
- AI(P4)는 **처음부터 쿼터제**. 무료 개방 + LLM 종량과금은 인프라 비용과 자릿수가 다르다
- **기존 학급 무료 유지(grandfather)** 원칙을 지금 정해둔다

### 6.6 사용자 수와 무관한 비용 축 (이미 잡혀 있음)
7월 청구의 92%는 배포 횟수에 비례하던 항목이었다 — Hosting 버전 잔재(51%)·Artifact Registry(25%)·Scheduler(16%).
`maxVersions:10` 과 cleanup 정책으로 조치됐다. **다시 새지 않는지만 주기 확인**하면 된다.

### 6.7 이 숫자를 믿어도 되는가 — 민감도 분석
읽기(1,775/일)만 Cloud Monitoring 실측이고 쓰기·CF호출·에그레스는 추정이다. 추정이 틀리면 결론이 흔들리는지 봤다.

## 7. 1인 운영 설계 — 이게 안 되면 개방은 실패한다

전국 개방의 실질적 상한은 서버 비용이 아니라 **운영자 한 명의 시간**이다.
3월 첫 주에 교사 200명이 동시에 학급을 만들다 막히면, 그건 200통의 문의다.

**그리고 그 한 명은 현직 교사다.** 교차검증에서 나온 지적 중 가장 날카로운 것이었다(§2.3 G12) —
3월 1~2주는 계정 분실·로그인 장애가 집중되는 시기인데, **바로 그 시기가 운영자 본인이
자기 학급 세팅과 담임 업무로 가장 바쁜 때**다. 대응 가능한 시간이 가장 적을 때 문의가 가장 많이 온다.
→ 그래서 §7.3 의 단계 개방은 선택이 아니라 **필수**이고, **3월 1~2주는 신규 유입을 아예 닫는 것**도 진지한 선택지다.
   (개학 직후가 아니라 3월 중순 이후에 문을 여는 편이 양쪽 모두에 낫다)

같은 개발자가 `iwplatform`(**EduMakers · 교사 AI 커뮤니티**, Next.js 16 + Cloudflare D1/R2/KV,
교원 인증·게시판·알림·2FA까지 구현)을 이미 만들어 두었다.
알찬의 지원·공지·요청 채널을 여기로 두면 **1:1 문의가 1:N 커뮤니티 답변으로 바뀐다.**

**단, 실측 확인 결과 아직 라이브가 아니다** — `edumakers.pages.dev` 응답 없음, 최신 커밋이

→ 따라서 "연결만 하면 되는 자산"이 아니라 **"배포만 하면 되는 자산"** 이다. 배포 자체가 하나의 작업이고,
   알찬 개방(2027-03)보다 **먼저** 서 있어야 지원 채널로서 의미가 있다. P2 기간에 배치한다.

## 9. 성공조건 — 검증 가능한 형태로

### 불변식 (어느 단계에서도 깨지면 안 됨)
1. **격리** — 어떤 학급의 학생·교사도 다른 학급 데이터를 읽거나 쓸 수 없다

   → 증명: `classes.usage` 계측으로 학급당 실측 비용을 산출, 임계 도달 시 알림

### 12.3 계획과 달랐던 것 (전부 실측이 뒤집었다)

**① `classes` 정본은 "신설"이 아니라 이미 있었다 — 그리고 정본이 아니었다.**
계획서 P0-1 은 `classes/{classCode}` 를 새로 만들자고 했는데, 열어보니 7건이 이미 있었다
(`teacherId`·`className`·`schoolName`·`studentCount`·`settings`). 문제는 존재가 아니라 **드리프트**다:

| 방향 | 내용 |
|---|---|
| classes 에 **없는데** 학생이 있음 | `QAZWSX12` 1건 — `settings/classCodes` 에도 없다. 그런데 **주급은 매주 나가고 있다** |
| classes 에**만** 있고 학생 0 | `6ZVKV3` · `CLASS2025` · `XHAWPR` 3건 |

계획서는 P0-2 로 "`getAllActiveClassCodes()` 를 classes 조회로 교체"를 넣었었다.
**오늘 그대로 했으면 QAZWSX12 의 주급이 조용히 끊겼다.** 그래서 정본을 바꾸지 않고
`logClassRegistryDrift()` 로 **차이만 매주 로그에 남긴다**. 몇 주 연속 "일치"가 찍히면 그때 교체하는 게 안전하다.
→ 교체는 P1 로 미룬다. 그때까지 이 로그가 유일한 근거다.

**② HTTP 엔드포인트를 크게 잘못 셌다.**
§2.3 에 "onRequest 가 다른 모듈에 38개 더 있다 — public 엔드포인트를 과소 집계했다"고 썼는데,
직접 세어보니 **전부 합쳐 22개**고 **22개 전부 토큰 인증**돼 있다. 무인증 0건.
진짜 문제는 다른 데 있었다 — **16곳이 토큰을 쿼리스트링으로 받는다.** 쿼리스트링의 시크릿은
Cloud Logging 요청 URL·프록시 액세스로그에 그대로 남는다(이 프로젝트는 실제로 스케줄러 토큰 3종을 한 번 잃은 전례가 있다).
그래서 헤더를 받도록 **추가**했다. 쿼리는 막지 않았다 — 기존 cron 잡이 깨지기 때문이다. 잡을 옮긴 뒤에 닫을 것.

**③ Tier-0 게이트가 느린 원인은 `node_modules` 가 아니었다.**
계획서 P0-6 은 "node_modules·.playwright-profile 제외"를 처방했는데, 실측하니 원인은 **git 이력**이었다.
이 저장소는 배포 산출물(`build/`)을 커밋한다(추적 파일 212개). gitleaks 의 git 모드는 커밋마다 미니파이 번들을
통째로 다시 스캔한다 — **49커밋에 65초, 86MB**. 커밋이 1,017개니 20분+ 가 나온다. 비용이 코드량이 아니라 **커밋 수**에 붙는다.

| 방식 | 시간 | 스캔량 |
|---|---:|---:|
| git 전체 이력 (종전 기본) | **20분+** | 190 MB |
| 작업트리 `--no-git` (새 기본) | **1.7초** | 13 MB |

게이트의 기본을 **작업트리**로 바꿨다. 게이트가 답해야 할 질문은 "지금 내보내려는 것에 시크릿이 있나"이고,
그건 작업트리·스테이지가 답한다. ⚠️ 대신 **"커밋했다가 지운 시크릿"은 못 잡는다** — 그건 게이트가 아니라 감사의 일이라
`PREFLIGHT_GITLEAKS_HISTORY=1` 로 분리했다(저장소 공개 전·키 로테이션 시에는 반드시 이걸로).
스캔 범위는 항상 출력한다 — 조용히 좁히지 않는다.
**결과: 게이트 전체가 20분+ → 66초.** 이제 상시로 돌릴 수 있다.

**④ rules 테스트는 `list`(쿼리)를 검증하지 못한다.**
교차학급 `list` 거부 케이스를 5건 넣었더니 전부 통과했다. 그런데 **같은 학급 ALLOW 카나리아를 넣어보니 그것도 실패했다** —
`:test` API 에 `method:"list"` 를 주면 평가할 문서가 없어 `resource.data.*` 가 무조건 오류→거부로 떨어진다.
즉 그 5건은 봉인이 아니라 **하네스 때문에** 통과하고 있었다. **잘못된 이유로 통과하는 테스트는 없느니만 못하다** — 걷어냈다.
필터된 쿼리가 실제로 통과한다는 근거는 대신 **프로덕션 선례**로 잡았다: `laws` 는 오래전부터 같은 규칙 패턴이고,
`OrganizationChart.js:130` 이 `where("classCode","==",classCode)` 로 목록을 정상 조회하는 라이브 기능이다.
쿼리 단위 검증은 Emulator 기반으로 옮길 때 제대로 붙인다(P2-16).

**⑤ 내 수정이 기능 하나를 깰 뻔했다 — 라이브에 문서가 0건이라 실측에서 안 보였다.**
`settings/{documentId}` 쓰기를 좁히면서 `salarySettings_{cc}` 와 `mainSettings` 만 살렸다.
그런데 같은 컬렉션에 **`menuLocks_{classCode}`(교사 메뉴 잠금)** 가 있었다 — 아직 아무 학급도 메뉴를
잠근 적이 없어서 **라이브 문서가 0건**이었고, 그래서 §12.1 의 문서 목록 실측에 잡히지 않았다.
그대로 배포했다면 교사가 메뉴를 잠그는 순간 조용히 실패했을 것이다.

자체 점검("이 규칙으로 무엇이 거부되나"를 코드에서 거꾸로 훑기)에서 잡아 고쳤고, 고치면서 보니
**원래 규칙(`: true` 분기)에서는 교사 A 가 B 반의 `menuLocks_B` 도 쓸 수 있었다** —
남의 반 학생 메뉴를 임의로 숨길 수 있었다는 뜻이다. 제대로 잠그니 구멍도 같이 닫혔다.

> 교훈이 반복된다: **없는 것은 세어지지 않는다.**
> 읽기 유출을 감사 3회가 놓친 이유도 "헬퍼 호출 횟수를 셌기 때문"(헬퍼를 아예 안 부른 컬렉션은 안 세어진다)이었고,
> 이번엔 "라이브 문서를 셌기 때문"(아직 안 만들어진 문서는 안 세어진다)이다.
> **실측은 존재하는 것만 보여준다. 코드에서 거꾸로 훑는 절차가 반드시 따라붙어야 한다.**

**⑥ 새로 쓴 규칙 안에서 구멍을 하나 만들었다가, 내가 쓴 테스트가 잡았다.**
goals 를 문서ID로 스코프하면서 `goalId == request.auth.token.get('classCode', '') + '_goal'` 이라고 썼다.
클레임이 **빈 문자열**이면 `'' + '_goal'` = `'_goal'` 이 된다 — 학급코드가 없는 계정이
`goals/_goal` 을 읽을 수 있다는 뜻이다. 라이브에 그 이름의 문서는 없어서 실제 유출은 0이었지만,
**규칙이 "빈 값이면 아무거나"로 읽히는 형태**를 남긴 셈이다.

같은 함정이 `settings` 쪽에도 있었다 — `'salarySettings_' + ''` = `'salarySettings_'`.
둘 다 `is string && size() > 0` 가드를 넣고 거부 테스트를 붙였다.

> **문자열 결합으로 스코프를 만들면 빈 값을 먼저 의심할 것.**
> 이건 검증자가 아니라 내가 쓴 DENY 케이스가 잡았다 — 봉인을 넣을 때 "통과해야 할 것"뿐 아니라
> **"막혀야 할 것"을 같은 커밋에서 쓰는 것**의 값이다.

#### 수정한 것

| # | 지적 | 계열 | 실제 영향 |
|---|---|---|---|
| 1 | **`musicRooms/{id}/playlist` 에 학급 검사가 통째로 없다** | Gemini·codex 동시 | 타 학급 학생이 **전국 무료 음악방에 곡을 무제한 등록**하고 남의 재생목록을 읽었다. 부모 방은 학급 스코프인데 **서브컬렉션만** 빠져 있었다 — 2026-07-19 하드닝이 top-level 만 훑은 자국 |

> **두 검증자가 정면으로 충돌한 지점이 있었다.**
> Gemini 는 "전체 키에 `hasOnly()` 를 걸지 마라(레거시 필드로 조용히 깨진다)",
> codex 는 "`hasOnly()` 만으로는 빈 문서 덮어쓰기를 못 막는다"고 했다. **둘 다 맞고, 둘 다 반쪽이다.**
> 답은 *무엇이 바뀌었나*(`diff().affectedKeys()`)와 *값이 정당한가*(`hasAll` + uid 일치 + timestamp + `<= request.time`)를
> **분리**하는 것이었다. 한쪽만 채택했으면 다른 쪽 결함이 그대로 남았다.
> — 이게 렌즈를 나눠 3계열을 돌리는 이유다. 합의가 아니라 **충돌**이 답을 만든다.

또 하나: 이 하트비트는 클라가 `.catch(() => {})` 로 실패를 통째로 삼키고 있었다.
규칙이 조여진 자리에서 침묵 실패는 곧 **원인 모를 시세 정지**가 된다 — 로그를 남기도록 고쳤다(`AuthContext.js`).

#### 등급을 낮춘 것 (오탐 아님 — 잔여로 기록)

**codex CRITICAL: 커스텀 클레임 stale 창(최대 1시간)** → **WARNING 으로 조정, 이번엔 안 고침.**
codex 논지는 맞다 — 학생이 학급을 옮겨도 옛 ID 토큰의 `classCode` 클레임이 최대 1시간 살아 있어
그동안 **옛 학급과 새 학급을 동시에** 읽을 수 있고, 악의적 사용자는 옛 토큰을 보관해 REST 로 쓸 수 있다.

그런데 Gemini 는 같은 사실을 보고 **OK** 로 판정했고, 그 근거가 결정적이다:
노출 범위가 *임의의 제3자 학급*이 아니라 **직전까지 본인이 정당하게 소속돼 있던 학급**이고, 쓰기는 전부 문서 기반 헬퍼라 차단된다.

**내 판단**: 이건 이번 변경이 만든 결함이 아니라 **읽기 비용 절감을 위해 의도적으로 도입한 구조**의 대가다
(`*Fast` 헬퍼는 이미 20여 개 컬렉션이 쓴다 — 요청당 `get(users/self)` 과금을 없애려고 만든 것). 되돌리면 그 절감이 통째로 사라진다.

### 12.6 2차 교차검증(운영·회귀 렌즈) 결과 — 그리고 내가 틀렸던 것

1차 검증(codex 보안·Gemini 코드)에 이어 **운영·데이터·배포 렌즈(Gemini)** 와 **회귀 렌즈**를 추가로 돌렸다.
회귀는 A~F 전부 OK. 운영 렌즈는 CRITICAL 0건이지만, **코드가 아니라 절차에서** 값을 냈다.

#### (1) 🔴 내 주석이 운영자를 오도하고 있었다 — 수정함
이월(`deferredClasses`) 처리에 나는 *"락을 풀어 다음 실행이 즉시 이어받는다"* 라고 썼다. **둘 다 틀렸다.**
- 자동 주급은 **월요일 1회뿐**이다. 스케줄러는 월·금(`30 8 * * 1,5`)에 뜨지만 본문 요일 가드가
  `day===1` 만 주급으로 보내고 금요일은 재산세·월세만 돈다. → "즉시"가 아니라 **7일 뒤**.
- `computeWeekKey` 는 1/1 부터 7일씩 끊어 **요일 정렬이 아니다**. 실측(2026-08): 월 W33 → 금 W34 로 **주중에 넘어간다.**
  그래서 다음 주 월요일엔 weekKey 가 달라져 **이월된 그 주가 아니라 새 주를 지급한다 → 그 주 주급은 영구 누락.**
- 복구 경로에도 함정이 있다: `weeklySalary?weekKey=` 는 백필 모드로 들어가 **학급별 스킵 가드를 끈다**(전 학급 재지급).
  올바른 복구는 **파라미터 없이, weekKey 가 넘어가기 전에** 재호출하는 것이다.
→ 주석과 error 로그 문구를 사실대로 고쳤다. **동작은 그대로**(이 경로는 4학급 기준 도달 불가한 안전망이다).

