## 2. 근본 원인 — "목록 전체를 읽어 화면엔 일부만 표시"

| 위치 | 읽던 양 | 실제 표시 |
|---|---|---|
| 경찰서 신고 | `limit(100)` → 당시 54건 전부 | 탭별 일부 |
| 나의 자산 거래내역 | 3개 소스 × `limit(50)` = 150 | **5건**(더보기 최대 20) |
| 타자 랭킹 | 학급 전원 user 문서 ~25 | 오늘 기록 있는 몇 명 |
| 할일 승인 | **상한 없음** + onSnapshot | 최근 몇 건 |
| 개인 상점 거래이력 | **상한 없음** | 최근 목록 |

**핵심은 절대량이 아니라 증가 곡선이다.** 신고·승인·거래는 1년 내내 쌓이므로
"방문 1회당 비용"이 학년 진행에 비례해 커지고, 거기에 학급 수가 곱해진다.
목표는 총량 감소가 아니라 **누적과 무관한 상수로 묶는 것**.

## 3. 적용한 수정

### 경찰서 (커밋 `3bdc3d0`, `b3a0069`)
- **미처리**(submitted/accepted)는 처리 대상이라 전량 유지 — `where in`만 쓰고 `orderBy`를 붙이지 않아
  자동 단일필드 인덱스로 처리.
- **처리 결과**는 최신 20건 + `startAfter` 기반 '▼ 이전 신고 더 보기'.
- **탭 카운트**는 `getCountFromServer`(완료 상태만 집계) 1읽기로 정확도 유지.
- 하위 로직이 쓰던 단일 `reports` 배열은 그대로 합성해 제공 → 호출부 무변경.
- 🐞 중간 오류 1건: 처음엔 "전체 − 미처리"로 계산했다가 **어느 탭에도 안 뜨는 레거시 상태 문서 25건**까지
  세어 54 → 79로 부풀었다. 완료 상태만 직접 집계하도록 수정해 54 복구.

### 나의 자산 (커밋 `3bdc3d0`)
`activity_logs` / `transactions` / `rootTransactions`를 각 50건(=최대 150문서) 읽고
병합·정렬 후 `slice(0, 20)`으로 20건만 쓰고 있었다.
세 소스 모두 timestamp 내림차순이므로 **자기 소스에서 21위 밖인 항목은 전체 상위 20에 들 수 없다**
→ 각 20건만 읽어도 결과가 수학적으로 동일. **150 → 60문서.**

### 타자 랭킹 (커밋 `3bdc3d0`) — 실측 56 → 5
- `getClassmates`로 학급 전원(~25문서)을 읽어 클라에서 거르던 것을
  `classCode == X && typingArcadeBestDay == today` 직접 조회로 교체.
  등가 조건 2개 조합은 자동 단일필드 인덱스로 처리된다
  (이 앱의 국고 조회 `classCode == X && isAdmin == true`가 인덱스 없이 동작 중인 것과 같은 형태).
- **증폭 제거**: 점수 저장 시 `updatedAt`을 갱신하던 것을 삭제. 그 필드는 다른 학생들의
  `getClassmates` 증분 동기화가 점수 변화를 감지하게 하려는 것이었는데, 대가로
  **한 명이 게임할 때마다 나머지 전원이 그 문서를 다시 읽는** 구조였다.
- 교사 제외 표시(`iAmExcluded`)는 좁힌 쿼리에 안 잡히므로 `userDoc` 기준으로 이동.

### 할일 승인 (커밋 `9185636`, `37c0c47`)
- `pendingApprovals` 구독에 상한이 없어 '승인됨'/'전체' 필터에서 **1년치 승인 이력 전부**를 읽고
  구독 상태로 유지했다 → `limit(50)`.
  (필요한 복합 인덱스 `classCode+requestedAt`, `classCode+status+requestedAt`는 이미 배포돼 있음)
- 🐞 그 부작용으로 대기 배지가 2 → 1로 과소 표시 → **배지를 `getCountFromServer` 1읽기로 분리**.
  원래도 '승인됨' 탭에선 배지가 아예 사라졌으므로 **기존보다 정확해졌다**(세 필터 모두 2로 일관 확인).

### 그 밖
- 개인 상점 판매/구매 이력(`activities`): 상한 없음 → `limit(100)`
- 학습 게시판 댓글: `limit(200)` → `limit(60)`

## 4. ⚠️ 설계 제약 — 새 복합 인덱스 금지

`.github/workflows/deploy.yml`은 **hosting · functions · storage · firestore:rules**만 배포하고
**`firestore:indexes`는 배포하지 않는다.** 복합 인덱스가 필요한 쿼리를 넣으면 배포 직후
목록이 통째로 안 보이는 사고가 난다. 그래서 이번 수정은 전부

- 등가 조건만 조합(`where ==` / `where in`) — 자동 단일필드 인덱스로 처리
- 또는 이미 배포된 복합 인덱스만 사용

하는 범위에서 설계했다. 인덱스가 필요한 개선을 하려면 **먼저 deploy.yml에
`firestore:indexes` 배포를 추가**할 것.

## 5. 사용자 제안 검토 — "학습 게임을 다른 사이트로 분리"

**효과 거의 없음, 비권장.** 실측상 오목 4문서, 아이템 상점 5문서로 게임 자체는 읽기를 거의 안 쓴다.
타자연습 56문서는 게임이 아니라 **랭킹이 학급 전원 문서를 읽어서**였고, 위 수정으로 5문서가 됐다.
분리하면 절감은 미미한 대신 보상(현금·쿠폰) 연동이 끊겨 학습 동기 설계가 무너진다.

## 6. 남은 것

- **부팅 139문서** — 구성: `getClassmates` ~25 + ItemContext ~29(상점18+인벤11) + 사용자 문서·설정류.
  ItemContext는 이미 sessionStorage 캐시(27분) + `catalogMeta` 버전 리스너로 잘 최적화돼 있다.
  TTL을 늘리는 건 **안전하지 않다** — 버전 리스너는 상점 카탈로그만 커버하고,
  마켓 리스팅/오퍼는 TTL이 유일한 신선도 장치다.
  추가 절감은 학급 명단 요약 문서(roster) 도입 같은 구조 변경이 필요하다.
- 학습 게시판 글 목록 `limit(100)` — 번호 페이지네이션이라 단순 축소 시 옛 글이 사라진다.
  경찰서처럼 커서 페이지네이션으로 바꾸면 해결되나, 번호 이동 UI와 총 페이지 수 계산을 함께 손봐야 한다.
