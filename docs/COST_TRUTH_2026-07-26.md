## 2. Hosting 저장용량의 정체 — ✅ 조치 완료

Hosting API 조회 결과 **버전 2,265개 / 30.35 GB**. 각 버전 85.1 MB(336파일)이고
실제로 서빙되는 건 최신 1개뿐, 나머지 2,264개는 전부 배포 이력이었다.
배포 1회 = +85 MB ≈ **월 +₩2**가 영구히 누적되는 구조.

### 실행한 조치
1. **보관 정책 설정** — `PATCH /v1beta1/sites/{site}/config?updateMask=maxVersions` → `maxVersions: 10`.
   프로젝트의 사이트 3개(`inconomysu-class`, `-85a88`, `-ad1cf`) 전부 적용. 이후 배포는 자동 정리된다.
2. **누적분 정리** — 라이브 릴리스가 가리키는 버전 + 최신 15개를 보호목록으로 잠그고
   나머지 2,250개 삭제. (사이트 `-85a88`, `-ad1cf`는 버전 0개라 대상 없음)

**결과: 30.35 GB → 1.25 GB** (보관 15개). 무료 한도 10 GB 안으로 복귀.
라이브 사이트 HTTP 200 정상 확인.

> ⚠️ 함정: Hosting API는 초당 쓰기 쿼터가 있어 동시 10으로 삭제하면 **429가 대량 발생**한다
> (1차 시도 959건 실패). 동시 3 + 요청당 120ms + 429 지수 백오프로 재시도해 전량 성공.

부수적으로 버전 1개가 85 MB인 것도 크다(아바타·재판방 PNG 에셋). 에셋 최적화는 별건.

## 3. Artifact Registry 2.05 GB — ✅ 조치 완료

Cloud Functions를 배포할 때마다 빌드 컨테이너 이미지가 `gcf-artifacts`에 쌓인다
(asia-northeast3 1.81 GB, us-central1 소량).

`PATCH /v1/projects/.../repositories/gcf-artifacts?updateMask=cleanupPolicies,cleanupPolicyDryRun`로
정리 정책 적용:
- `keep-recent`: `action=KEEP`, 최근 3개 버전 보존
- `delete-old`: `action=DELETE`, 7일(604800s) 경과분 삭제
- `cleanupPolicyDryRun=false` (실제 삭제 모드)

> ⚠️ 함정: `mostRecentVersions`만 주고 `action`을 빠뜨리면 400 `invalid cleanup policy action`.
> KEEP 정책에도 `action: "KEEP"`을 명시해야 한다.

정리는 비동기로 수행되므로 용량 감소는 하루 정도 뒤 반영된다.

## 7-3. "나머지 89%"를 실측했다 — 낭비가 아니었다

### 계측 방법
실제 세션을 만들어 Cloud Monitoring 1분 해상도로 쟀다(2026-07-26 13:42~13:46 UTC).
대시보드 → 은행 → 아이템 → 나의자산 → 학습게시판 → 주식거래소 → 대시보드 (7회 이동).

```
13:43=25  13:44=29  13:45=69  13:46=128   합계 251
```

**7페이지 이동 = 251읽기 → 페이지 이동 1회당 약 36읽기.**
40명 × 하루 30회 이동 × 36 ≈ 43,000 — 관측된 수업일 35,000~71,000과 맞아떨어진다.

### 이미 최적화돼 있음을 확인한 것들
- **경찰서**: `auth.classmates`가 있으면 학급명단 쿼리를 아예 건너뛰고, 그마저도 `cacheKey`로 세션 캐시.
- **학급 명단**(`/users WHERE classCode`): 주 **77회** 실행뿐. 40명 기준 1인당 주 2회 —
  AuthContext의 증분 동기화(`updatedAt > lastSync`)가 잘 작동하고 있다는 뜻.
- **ItemContext**: sessionStorage 27분 캐시 + `catalogMeta` 버전 리스너. 1인당 하루 약 5회 호출.
- **전역 컬렉션 구독 헬퍼**(`subscribeToCollection`)는 호출부가 없는 죽은 코드 — 팬아웃 없음.
- `getAllUsersDocuments`(필터 없는 전체 users)도 실호출부 없음. 남은 필터 없는 조회 2건은
  superadmin·권한관리 화면 전용이라 학생 경로와 무관(주 34회·7회).

### 결론
**남은 89%는 제거할 낭비가 아니라, 40명이 하루 수십 번 화면을 여는 실제 데이터 로딩 비용이다.**
"목록 전량 조회" 같은 명백한 낭비는 어제·오늘 라운드에서 이미 걷어냈다.

여기서 더 줄이려면 **화면당 필요한 문서 수 자체를 줄이는 구조 변경**이 필요하다:
학생별·학급별 요약(비정규화) 문서를 서버가 유지하고 화면은 그 1~2문서만 읽는 방식.
효과는 크지만(페이지당 36 → 한 자릿수) 자산 정합성 위험이 있어 별도 결정·검증이 필요하다.

### ⚠️ 도구 한계: 쿼리 통계는 총량 근거로 쓸 수 없다
40개 쿼리 전체 합계 **61,282** vs 같은 기간 실제 **205,756** — **30%만 설명**한다.
순위 파악용으로만 쓰고, 총량·절감 검증은 반드시 Monitoring API로 할 것.

## 7-5. ⚠️ 사고 기록 — 감사 스크립트가 무료 한도를 혼자 태움 (2026-07-27)

ETF·채권 거래 이력을 보려고 세션 스크래치의 헬퍼로 `listDocs("activity_logs", 300)`을 호출했다.
`pageSize=300`을 **"300건 표본"으로 착각**했으나, 헬퍼는 `nextPageToken`을 끝까지 따라가
컬렉션을 **전량** 읽는다. 두 번 호출 → **35,745문서 × 2 ≈ 71,500읽기.**

```
09:20=6,110  09:21=29,574  09:22=25,046  09:23=10,957
오늘 누계 74,981 (무료 한도 50,000) — 그중 96%가 이 스크립트
```

- 금액 피해: 초과 약 25,000읽기 × 서울 단가 = **약 ₩13**로 미미.
- **진짜 피해는 계측 오염** — 어제 넣은 폴러 가드의 절감 효과를 오늘 그래프로 검증할 수 없게 됐다.
  검증은 하루 미룬다.
- 조치: 헬퍼에 `maxDocs`(기본 3,000) 하드 상한 + 초과 시 경고 후 중단.
- 교훈: **진단 스크립트도 프로덕션 읽기를 쓴다. 측정 행위 자체가 측정을 오염시킬 수 있다.**
  출력에 "N건 표본"이라 찍혔는데 N이 예상보다 크면 그 자리에서 멈출 것.
